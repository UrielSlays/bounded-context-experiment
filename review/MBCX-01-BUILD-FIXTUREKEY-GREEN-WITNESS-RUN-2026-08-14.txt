THE ONE INVARIANT THIS FOLD ADDS
--------------------------------
A production root of trust is recognised by its KEY, not by a flag in a document.
A ProductionVerifierContext refuses, by name, any anchor whose public key is
COMMITTED TO THIS REPOSITORY - whatever fixture_only says, through in-code wiring or
through the MBCX01_BUILD_OWNER_TRUST_ANCHOR configuration path, and regardless of
how the PEM is line-wrapped. The known-key set is DERIVED from the committed
*.fixture.json anchor documents themselves
(mbcx01_build_trust_anchor.committed_fixture_key_material), never hand-listed.

Placement is not invented: MITRE CWE-1291 ("Public Key Re-Use for Signing both Debug
and Production Code", PeerOf CWE-321) puts the mitigation at Architecture-and-Design,
i.e. at CONTEXT CONSTRUCTION.

Same framing as the RED bank: MBCX-01 has no threat model and no untrusted caller
(MBCX-01-BUILD-ADVERSARY-PREMISE-CORRECTION-2026-08-14.md). This is a
scientific-validity / self-deception guard - the ceremony is when a human hand-writes
the anchor document, and copying the committed example is the obvious way to do it -
not an access-control boundary. Anything running arbitrary Python in the verifying
interpreter still reaches past it (object.__new__ + object.__setattr__ around a
context, and configure_production_verifier_context is an isinstance check); that
actor is the box owner and remains a NAMED, ACCEPTED residual under the T2 ceiling.
